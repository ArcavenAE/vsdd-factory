# S-25.02: Artifact Sharding Layer 2 — Size-Triggered Shard Rotation for Cycle Artifacts

## Narrative

- **As a** factory pipeline operator who has Layer 1 (INDETERMINATE markers, BC-1.18.001-004) deployed
- **I want** the append-only cycle artifacts (decision-log.md, burst-log.md, lessons.md,
  session-checkpoints.md) AND `BC-INDEX.md`'s two independent size drivers (its frontmatter
  `changelog:` array and its per-subsystem body tables) to be automatically split into capped
  shards when they approach the validator-completion fuel envelope, with a deterministic,
  native-dispatcher size/item-count rule enforced by a PreToolUse gate rather than LLM-side
  awareness
- **So that** no shard ever exceeds the size at which fuel-exhaustion INDETERMINATE events fire,
  eliminating the root cause of Layer-1 marker writes BY CONSTRUCTION (for both mechanism-A
  append-logs and BC-INDEX's own size drivers — BC-INDEX alone produced 45.2% of the first 708
  observed `plugin.indeterminate` events) and making the Cohort B validators
  (`validate-burst-log`'s Edit/Write/MultiEdit arm, `regression-gate`, `convergence-tracker`) safe
  to flip to `failure_policy = "fail-closed"`

## Context / Feature Summary

**Registered at:** F3 story-decomposition burst, validation-integrity-layer1 cycle, 2026-08-30
(story-writer). **Populated at:** F3 incremental-stories burst, 2026-09-06 (story-writer), from
the F2-converged, human-ratified spec. Source: ADR-047 §Decision 8b (originally: Ratified Future
Phase Layer 2) elaborated into ADR-051 (accepted v1.8, D-1167) — Two-Mechanism Size-Triggered
Shard Rotation for Cycle Append-Logs and BC-INDEX Sharding.

**Why Layer 2 follows Layer 1 (not concurrent):** Layer 1 instruments the INDETERMINATE failure
mode (detects and surfaces it). Layer 2 attacks the root cause (large artifacts). Layer-1
`plugin.indeterminate` production forensics (available after S-25.01 merged) confirmed
`BC-INDEX.md` alone accounts for 45.2% of the first 708 observed events, directly shaping ADR-051's
decision to widen scope beyond the original mechanism-A-only draft to also cover BC-INDEX's two
independent size drivers (D-1166, human widest-scope decision).

**Two mechanisms, three artifact shapes, one native gate (ADR-051 §Decision 1):**

1. **Mechanism A — byte-size-denominated shard rotation for the four append-only cycle logs**
   (`decision-log.md`, `burst-log.md`, `lessons.md`, `session-checkpoints.md`). A `stat()`-only
   size check (BC-1.18.005) triggers a roll-before-write (BC-1.18.006: publish the current
   content as a NEW sealed file via copy, then atomically replace the canonical file's content
   with empty in place — never a rename-away) plus retention/compaction (BC-1.18.007) plus a
   mandatory one-time backfill-split of the four pre-existing oversized files (BC-1.18.008).
2. **Mechanism B1 — item-count-denominated rotation of `BC-INDEX.md`'s frontmatter `changelog:`
   array** (BC-INDEX's dominant size driver, 177,305 of 539,713 bytes measured 2026-09-05), reusing
   the already-shipped `rotate_changelog` primitive (ADR-049 §Decision 6, CAP-042) via a
   single-actor block-and-retry contract (BC-1.18.009) plus a governed one-time cold-start backfill
   migration (BC-1.18.012, ~1,997 unrotated items).
3. **Mechanism B2 — per-subsystem body-table sharding of `BC-INDEX.md`'s ten `### SS-NN` sections**
   into individually-addressable shard files, with zero-lookup first-level addressing (via the
   already-authoritative ARCH-INDEX BC-S-prefix→SS-NN mapping, POLICY 6) and manifest-based
   second-level sub-sharding for the two subsystems (SS-05, SS-06) already over cap on section size
   alone (BC-1.18.010), plus a governed one-time migration (BC-1.18.011).

**Shard cap formula (production-grade; ADR-051 §Decision 2, BC-1.18.005 Postcondition 4/6):**
```
shard_cap_bytes <= (PRACTICAL_FUEL_CEILING / WORST_CASE_FUEL_PER_BYTE) - MAX_SINGLE_RECORD_BYTES - SAFETY_MARGIN
```
Constants are PROVISIONAL until the F4 synthetic calibration harness runs (owned by
performance-engineer, co-run with implementer per BC-1.18.005 Postcondition 7); the formula SHAPE
is locked now (illustrative worked value: 49,152 bytes / 48 KiB), the numbers are not. Effective
per-artifact cap is the MINIMUM across every Cohort B validator that reads that artifact
(Cross-Validator Minimum Rule, BC-1.18.005 Postcondition 5).

**Three governed one-time migrations are MANDATORY companions, not follow-ups** (BC-1.18.008 for
mechanism A, BC-1.18.011 for B2, BC-1.18.012 for B1) — per CLAUDE.md's production-grade default, a
gate that only prevents FUTURE overflow without retroactively shrinking the artifacts already
producing the majority of observed INDETERMINATE events is an incomplete delivery of this story's
own stated purpose.

**Cohort B flip is the capstone (BC-7.08.001):** once BC-1.18.005/006's gate is F4-locked AND
BC-1.18.008's backfill-split has COMPLETED (hard sequencing gate — flipping fail-closed before the
pre-existing oversized files are split would immediately re-trigger the exact INDETERMINATE loop
this story exists to eliminate), `hooks-registry.toml` assigns `failure_policy = "fail-closed"` to
exactly three registry entries: `validate-burst-log`'s `^(Edit|Write|MultiEdit)$` arm ONLY (its
sibling `^Bash$` git-commit chain-detection arm is exec-free, unrelated, and explicitly out of
scope), `regression-gate`, and `convergence-tracker`.

**SS-04 touchpoint (ADR-051 §Decision 6, adjudicated 2026-09-06):** the retention/compaction
policy's validator enumeration directly audits four SS-04-owned WASM crates
(`validate-dispatch-advance`, `validate-state-structure`, `validate-closes-completeness`,
`validate-cross-site-correspondence`) for archival-scheme correctness, and imposes a new
archive-inclusive-glob obligation on POLICY-1's (`append_only_numbering`) SS-04-adjacent
enforcement path (`consistency-validator`/adversary-prompt agent level, `lint_hook: null`) — the

## Acceptance Criteria

### AC-001: Native `stat()`-only deterministic size-trigger, zero-cost bypass, match-first blast-radius scoping (traces to BC-1.18.005 postcondition 1, postcondition 2, invariant 3, edge cases EC-018, EC-019)

A native (non-WASM) dispatcher function, invoked from the PreToolUse handling path before the
registry-driven plugin loop, checks the tool call's target path against a `[[shard]]` config
table. An unmatched path returns `Continue` immediately with zero `stat()` calls (zero-cost bypass
for the ~99% of `Edit`/`Write`/`MultiEdit` calls Layer 2 does not touch). A matched path reads
ONLY the current shard's byte size via filesystem metadata — never file content, never a WASM
sandbox, never a fuel budget — so the check itself is structurally incapable of producing a
`plugin.timeout`/`plugin.indeterminate` event.

**Match-first blast-radius scoping (added BC-1.18.005 v1.12, S-25.02 Phase F4 LOCAL adversary
cluster-1 pass-6 finding F-C1-P6-001, LOW pending-intent, product-owner adjudication).**
`ShardRegistry::load()` performs STRUCTURAL TOML deserialization only; the new `validate_entry(&
ShardEntry)` function carries all semantic checks (EC-009/EC-011/EC-012/EC-013/EC-015/EC-016/
EC-017) and runs AFTER `find_matching_entry` resolves the current dispatch's target path, and ONLY
against the MATCHED entry. An unmatched target returns `Continue` — and a target matching a
DIFFERENT, well-formed entry proceeds under normal gate logic — even if a SIBLING `[[shard]]`
entry is semantically malformed: a sibling's config typo no longer blocks unrelated dispatches
(EC-018). The one residual exception is whole-file STRUCTURAL TOML parse failure — invalid TOML
syntax, or any entry omitting a non-`Option`-typed field required for `toml::from_str` to succeed
(`artifact_stem`, `shard_cap_bytes`, or any of the four `cap_formula_inputs` fields) — which STILL
fails loud (`HookResult::Error`) for every `Edit`/`Write`/`MultiEdit` dispatch while the config
file exists, matched or not, because `find_matching_entry` cannot run at all without a
successfully deserialized registry (EC-019). This narrows the ENTRY-SCOPE of every existing
fail-loud check cited elsewhere in this story (AC-005, AC-023) from "every entry in the file,
every dispatch" to "the entry matched against the current dispatch's target path, evaluated at
entry-match time" — it does NOT change any cited check's substantive fail-loud outcome, numeric
threshold, or "before any write against that artifact" timing guarantee (BC-1.18.005 postcondition
1 "Blast-radius scoping" sub-paragraph, invariant 3 extension).

### AC-002: Per-tool-semantics projected-size formula (traces to BC-1.18.005 postcondition 3, edge case EC-005)

`projected_size` is computed per-tool: for `Write`, `projected_size = len(content)` alone
(`current_shard_bytes` is NOT added — `content` is the complete post-apply file). For
`Edit`/`MultiEdit`, `projected_size = current_shard_bytes + net_delta_bytes` (the net length delta,
summed across all edit blocks for `MultiEdit`, which may be negative). `projected_size <=
shard_cap_bytes` (inclusive boundary) returns `Continue`; `> shard_cap_bytes` triggers the roll
sequence.

**Documentary note (non-AC, no code obligation — BC-1.18.005 v1.11 Postcondition 3 "Known formula
gap").** The `Edit`/`MultiEdit` net-delta formula above computes a SINGLE-occurrence
`len(new_string) - len(old_string)` delta and does not account for `replace_all: true`'s occurrence
multiplicity (actual on-disk delta is `occurrence_count(old_string, current_file_content) x
(len(new_string) - len(old_string))`), which can under-count `projected_size` for a bulk
`replace_all` edit. Product-owner has explicitly adjudicated this gap DEFERRED to BC-1.18.006
(cluster 2) — not a cluster-1/S-25.02 obligation — because closing it requires a full-content read
that departs from Postcondition 2's stat()-only guarantee and because this cluster's trigger is
non-blocking today (a fired trigger only `tracing::warn!`s and returns `Continue`; the roll/block
outcome does not exist until BC-1.18.006 lands). No AC or code change follows here; see
BC-1.18.005 Postcondition 3's "Known formula gap" sub-paragraph and Related BCs for the explicit
deferral anchor.

### AC-003: Cross-Validator Minimum Rule (traces to BC-1.18.005 postcondition 5)

An artifact's effective `shard_cap_bytes` is the MINIMUM across every Cohort B validator that reads
it (e.g., `burst-log.md`'s cap is `MIN(cap_for(validate-burst-log), cap_for(regression-gate),
cap_for(convergence-tracker))`; `decision-log.md`/`lessons.md`/`session-checkpoints.md`'s cap
excludes `validate-burst-log`'s per-plugin cap, since that validator does not read them). A single
global cap across all four mechanism-A artifacts MUST NOT be used.

### AC-004: Cap-formula constants are config, not hardcoded — F4 calibration harness (traces to BC-1.18.005 postcondition 6, postcondition 7)

`PRACTICAL_FUEL_CEILING`, `WORST_CASE_FUEL_PER_BYTE`, `MAX_SINGLE_RECORD_BYTES`, and
`SAFETY_MARGIN` are read from the `[[shard]]` config, never embedded as Rust constants in
`shard_manager.rs`. A synthetic calibration harness (performance-engineer, co-run with
implementer) locks the final numeric values before this BC's postconditions are treated as final,
re-run whenever `DEFAULT_FUEL_CAP` changes at the operator level; if a Cohort B plugin's fuel/byte
relationship is superlinear, `WORST_CASE_FUEL_PER_BYTE` uses the LOCAL marginal rate at the largest
tested size, never the global average slope.

### AC-005: Item-count trigger for the `"frontmatter-changelog-array"` shape, with `low_water_mark` config (traces to BC-1.18.005 postcondition 1, postcondition 8, edge cases EC-008, EC-010, EC-011, EC-012, EC-014, EC-016, EC-020, EC-021, EC-022)

The SAME native gate dispatches to an item-count trigger (`current_item_count + 1 > N`) when the
`[[shard]]` config entry declares `shape = "frontmatter-changelog-array"`, distinguished from the
`"flat"` byte-size shape by that field alone (never content-sniffed). A sibling `low_water_mark`
config value (default `floor(N/2)` when omitted) declares the rotation TARGET — never `N` itself
and never a hardcoded `N-1`. Fail-loud (`HookResult::Error`) on `low_water_mark >= N` (the `== N`
boundary included) or negative; any legal value in `(floor(N/2), N)` up to and including `N-1`
loads normally but emits a non-fatal `tracing::warn!` amortization advisory.

**Missing-file / first-write create path (added S-25.02 Phase F4 LOCAL adversary cluster-1 pass-3
finding F-C1-P3-001, product-owner adjudication, BC-1.18.005 v1.9).** When the
`"frontmatter-changelog-array"`-shaped target artifact does not yet exist on disk — a legitimate
first-ever `Write` that CREATES the artifact — `read_changelog_item_count` MUST map
`io::ErrorKind::NotFound` to `Ok(0)`, treating the not-yet-existing artifact as holding 0 existing
changelog items, mirroring EC-004's flat-shape missing-file-is-zero precedent (BC-1.18.005
postcondition 8's missing-file/first-write sub-bullet). The item-count trigger then evaluates
`current_item_count + 1 = 0 + 1 = 1 > N`, which is `false` for any config `N >= 1`, so the create
always returns `Continue` — it is NEVER hard-blocked as `HookResult::Error`. Any OTHER `io::Error`
kind encountered reading an EXISTING file (a malformed frontmatter fence, a permissions failure,
etc.) is UNCHANGED and still propagates as `HookResult::Error` (fail-loud) — ONLY `NotFound` is
special-cased.

**Load-time fail-loud enforcement of `N`'s presence (added S-25.02 Phase F4 LOCAL adversary
cluster-1 pass-4 finding F-C1-P4-002, product-owner adjudication, BC-1.18.005 v1.10).** For every
`"frontmatter-changelog-array"`-shaped `[[shard]]` config entry, `ShardRegistry::load()` MUST
validate that `entry.n` is `Some` — fail-loud `HookResult::Error` (new `ShardConfigError::MissingN
{ artifact_stem }`) on `None` — evaluated BEFORE the entry's `low_water_mark` is examined. This
closes a load-time gap: the entry's `low_water_mark` numeric-range validation (`0 <= low_water_mark
< N`) is only well-defined once `N` is known, and the prior destructure-and-short-circuit pattern
validated `low_water_mark` only when BOTH `entry.n` and `entry.low_water_mark` were `Some` — an
entry omitting `N` AND declaring an out-of-range `low_water_mark` passed load-time validation
entirely, with the error deferred to the first gate-time write. `N`'s presence is now an
unconditional, load-time, shape-scoped check evaluated first, independent of whether
`low_water_mark` is present: every such entry either (a) fails loud on a missing `N` at load time,
or (b) has `N` present, in which case the existing `low_water_mark` range validation (EC-011) runs
exactly as before — no entry can silently load with BOTH a missing `N` and an out-of-range
`low_water_mark` undetected.

**Present-but-fenceless target — permissive `Ok(0)`, already shipped (added S-25.02 post-merge
propagation burst, PR #818 cluster-1 fix-burst finding B1, product-owner adjudication, BC-1.18.005
v1.13 backfill of an already-shipped code ruling).** When a `"frontmatter-changelog-array"`-shaped
target artifact EXISTS on disk but carries NO well-formed `---`/`---` frontmatter fence at all — no
line-anchored opening fence, or an opening fence with no line-anchored closing fence found before
end-of-file — `read_changelog_item_count` MUST return `Ok(0)` rather than propagating an

### AC-023: Load-time fail-loud enforcement of cap-vs-formula inequality (traces to BC-1.18.005 postcondition 9, edge cases EC-013, EC-015, EC-017)

For EVERY `[[shard]]` config entry — regardless of `shape` (Postcondition 8 already establishes that

`"frontmatter-changelog-array"` shape, so this check is NOT `"flat"`-shape-only) — `ShardRegistry::load()`
independently recomputes `compute_shard_cap_bytes(entry.cap_formula_inputs())` from that SAME entry's
own four parsed formula inputs (`practical_fuel_ceiling`, `worst_case_fuel_per_byte`,
`max_single_record_bytes`, `safety_margin`) and compares it against that entry's own declared
`shard_cap_bytes`. If the declared `shard_cap_bytes` is GREATER than the computed ceiling, `load()`
returns `HookResult::Error` — the misconfigured entry is REJECTED; it is NEVER silently accepted and
NEVER silently clamped down to the computed ceiling. A declared `shard_cap_bytes` exactly EQUAL to the
computed ceiling (boundary case) loads normally (`Ok`) — the comparison is inclusive of the boundary,
mirroring EC-002's inclusive-boundary precedent for the per-write trigger. This is a load-time
misconfiguration guard over a `[[shard]]` entry's own internal consistency between its declared cap and
its own declared four inputs; it does not require or perform any re-derivation of the F4 harness's
calibration itself (BC-1.18.005 Postcondition 6/7 continue to own HOW the constants are measured).

**Divisor-door closure — `worst_case_fuel_per_byte` finiteness/positivity guard (added S-25.02
Phase F4 LOCAL adversary cluster-1 pass-4 finding F-C1-P4-001, product-owner adjudication,
BC-1.18.005 v1.10).** BEFORE computing `compute_shard_cap_bytes(entry.cap_formula_inputs())` for
any `[[shard]]` entry, `ShardRegistry::load()` MUST validate
`worst_case_fuel_per_byte.is_finite() && worst_case_fuel_per_byte > 0.0` (BC-1.18.005 postcondition
9's formula-input-validity precondition). A non-finite value (`NaN`, `inf`, `-inf`) or a value
`<= 0.0` — including `0.0` itself, which saturates the division to `+inf` and the subsequent `as
u64` cast to `u64::MAX`, defeating the cap-vs-formula comparison above for ANY declared
`shard_cap_bytes` — fails loud with `HookResult::Error` (new
`ShardConfigError::InvalidWorstCaseFuelPerByte { artifact_stem, worst_case_fuel_per_byte }`),
evaluated BEFORE the cap-vs-formula ceiling computation this AC's first paragraph describes. No
analogous check is required for `practical_fuel_ceiling`, `max_single_record_bytes`, or
`safety_margin` — all three are `u64`-typed (TOML deserialization already excludes non-finite/
negative values), and a degenerate `0` on any of them drives the computed ceiling toward the safe
(more conservative) direction, never toward the exploitable `u64::MAX` widening this guard closes.

**Residual divisor-door closure — saturated computed-ceiling guard (added S-25.02 Phase F4 LOCAL
adversary cluster-1 pass-5 finding F-C1-P5, product-owner adjudication, BC-1.18.005 v1.11).** The
guard immediately above (`worst_case_fuel_per_byte.is_finite() && > 0.0`, EC-015) is NECESSARY but
INSUFFICIENT to close the divisor-door: a LEGAL tiny-positive divisor (e.g.
`worst_case_fuel_per_byte = 1e-300`) passes that guard yet still drives the RAW division
`practical_fuel_ceiling as f64 / worst_case_fuel_per_byte` to a value so large that the subsequent
`.floor() as u64` cast saturates to `u64::MAX` — reproducing the IDENTICAL failure mode the EC-015
guard exists to close, since the resulting near-`u64::MAX` computed ceiling passes ANY declared
`shard_cap_bytes` through the `CapExceedsFormulaCeiling` comparison above. `ShardRegistry::load()`
MUST, for every entry that passes the EC-015 guard and BEFORE the `CapExceedsFormulaCeiling`
comparison is evaluated, independently evaluate this SAME raw pre-cast division result and reject
the entry — `HookResult::Error` (new `ShardConfigError::FormulaCeilingSaturated { artifact_stem,
practical_fuel_ceiling, worst_case_fuel_per_byte }` variant, distinct from
`InvalidWorstCaseFuelPerByte`) — if that raw value is non-finite (`!result.is_finite()`) OR is
`>= u64::MAX as f64` (the saturation boundary of the subsequent lossy cast). `load()` MUST NEVER
silently accept a saturated ceiling and MUST NEVER silently substitute a fallback ceiling. Together
with the EC-015 divisor-legality guard, this closes the divisor-door completely (EC-017).

field) and set `sealed_retroactively = true` if `bytes_at_seal > shard_cap_bytes`, else `false` (or
omit, per Postcondition 5's default) — never a hardcoded `false` regardless of size. This closes a
genuine mislabeling gap: a PROSPECTIVE roll (Postcondition 1's normal pre-write path) can never
seal over-cap content (Postcondition 3's unconditional per-shard cap guarantee), so
`bytes_at_seal > shard_cap_bytes` on a recovered entry is proof-by-construction that the seal was
retroactive — the inference is used only in that unambiguous `>` direction. Without this
correction, `E-SHD-007`'s filesystem-only reconciliation (blind to which roll produced the
orphaned file) would mislabel a genuinely over-cap shard as cap-guaranteed, the exact ambiguity
`sealed_retroactively` (Postcondition 5) exists to prevent.

**Stable-Cap Precondition — Invariant 7's inference is exact only under a stable `shard_cap_bytes`
(NEW, BC-1.18.006 v1.5→v1.6, cluster-2 LOCAL adversary pass-2 finding F-C2-P2-004, MINOR, edge case
EC-020).** The `bytes_at_seal > shard_cap_bytes ⇒ sealed_retroactively = true` inference above is
exact only while `shard_cap_bytes` remains STABLE across a shard's seal-to-reconciliation window;
BC-1.18.005 Postcondition 6/AC-004 permits the F4 calibration harness to re-lock the cap when
`DEFAULT_FUEL_CAP` changes — a rare, deliberate, phase-gated administrative event, never a
continuously runtime-mutable parameter. If an `E-SHD-007`-orphaned, un-indexed sealed shard survives
across such a re-calibration boundary before its own reconciliation runs, the inference compares
`bytes_at_seal` (fixed under the OLD cap regime) against the NEW, live `shard_cap_bytes`, producing
two possible mislabels: a cap LOWERED between seal and reconciliation mislabels a legitimately
prospective seal `sealed_retroactively=true` (a FALSE POSITIVE); a cap RAISED mislabels a genuinely
retroactive seal `sealed_retroactively=false`/omitted (a FALSE NEGATIVE). Both mislabels are
ACCEPTED, DOCUMENTED, and judged operationally negligible: (1) the mislabeled field is a historical
audit-trail annotation only, gating no hard structural guarantee — Invariant 6's canonical
zero-bytes-after-roll guarantee and the sealed-shard content-preservation guarantee are computed
independently of this flag and are unaffected in either direction; (2) the mislabel requires the
CONJUNCTION of an already-rare `E-SHD-007` crash surviving specifically across an already-rare,
deliberately-gated F4 recalibration boundary before that same orphaned entry's own reconciliation
runs; (3) the bound is precisely testable — the inference is GUARANTEED correct whenever
`shard_cap_bytes` was unchanged throughout `[sealed_at, reconciliation_time]`. This is a documented,
bounded, accepted design tradeoff, not a deferred defect: no code change follows from this note — the
current self-heal inference implementation (this AC's paragraph above) is already correct under this
now-explicit stable-cap precondition; this is a spec-only, documentary clarification and carries no
new Red Gate test obligation.

### AC-025: Next-dispatch leading-probe backstop for a missed catch point (i), with a dedicated `Write`-arm data-loss guard and a uniform fail-loud backstop-probe stat-failure disposition (traces to BC-1.18.006 postcondition 7, edge case EC-015, EC-017, EC-019, invariant 8)

**NEW, PENDING — S-25.02 cluster-2 F3 AC population burst, product-owner BC-1.18.006 v1.4;
EXTENDED cluster-2 LOCAL adversary pass-1 (F-C2-P1-002, MAJOR), BC-1.18.006 v1.4→v1.5. This AC
describes code that does NOT yet exist; it is a new unimplemented Red Gate obligation, TDD'd from
scratch under this story's `tdd_mode: strict` — NOT documentary/already-shipped backfill.**

Before evaluating BC-1.18.005's own trigger for ANY subsequent `Edit`/`Write`/`MultiEdit` dispatch
against a matched artifact, the gate first checks whether the CURRENT on-disk size already exceeds
`shard_cap_bytes`. This is a state that is structurally impossible to persist under the normal
pre-write block-and-retry flow, and should already have been resolved by AC-024's catch point (i),
but can transiently survive a dispatcher process crash between a `replace_all: true` write's
completed application and catch point (i)'s own execution. If the check finds the current on-disk
size already over cap, the gate executes the SAME retroactive four-step roll sequence AC-024
specifies BEFORE evaluating the new call's own trigger. Together, AC-024 and this AC bound the
canonical file's observable-over-cap window to at most one subsequent matched dispatch — never
indefinitely, never spanning more than one subsequent matched dispatch — the sole, explicitly
bounded exception to Postcondition 3's "no shard is ever observed in an over-cap state" structural
guarantee, applying ONLY to this narrow `replace_all: true` case; every other call class this
story's mechanism-A ACs govern retains Postcondition 3's unconditional guarantee.

**CORRECTED — the probe cost is per-tool, not uniformly free; `Write` requires a DEDICATED `stat()`,
never a reused one (BC-1.18.006 v1.4→v1.5, cluster-2 LOCAL adversary pass-1 finding F-C2-P1-002,
MAJOR, edge case EC-017).** The withdrawn v1.4 wording above ("reusing the SAME `stat()`
BC-1.18.005 Postcondition 2 already performs") is TRUE for `Edit`/`MultiEdit` — whose Postcondition
3 formula, `projected_size = current_shard_bytes + net_delta_bytes`, already `stat()`-reads
`current_shard_bytes`, so this AC's check reuses that already-read value at zero added cost — but
was WRONG for `Write`: `Write`'s Postcondition 3 formula is `projected_size = len(content)` alone,
with NO `stat()` of the canonical file anywhere in BC-1.18.005's own `Write` trigger path, so there
is no existing stat-read for this AC to reuse. Left uncorrected, this was a real DATA-LOSS gap, not
merely a wording inaccuracy: after a dispatcher crash leaves the canonical file over cap and
un-sealed (AC-024's own EC-015/EC-036 scenario), a subsequent `Write` whose own `content` is
under-cap would apply directly against the canonical file — REPLACING, and permanently DESTROYING,
the un-sealed over-cap history, since no roll was ever attempted for self-heal to catch (self-heal
reconciles orphaned ROLLS; it has nothing to reconcile if no roll was ever attempted). Under
CLAUDE.md's production-grade default (no version of this gate may lose history), this AC's backstop
therefore performs its OWN dedicated, bounded `stat()` of the canonical file BEFORE applying a
`Write` — an ADDITIONAL probe specific to the `Write` arm, NOT a change to BC-1.18.005's stat-free
`Write` trigger formula (which is UNCHANGED: this dedicated stat feeds ONLY this AC's over-cap
check, never `projected_size`). For `Edit`/`MultiEdit`, the backstop remains cost-free (reuses the
existing stat), unchanged from the original design intent. Net cost: one bounded `stat()` call
added per `Write` against a matched artifact (independent of artifact size, since `stat()` never
reads file content); zero added cost for `Edit`/`MultiEdit`. With this dedicated probe in place,
catch point (ii) detects the crash-orphaned over-cap state and executes the retroactive four-step
roll (sealing the orphaned content with `sealed_retroactively: true`, AC-024) BEFORE the `Write`'s
own `content` is ever applied — closing the data-loss path where an unguarded `Write` would
otherwise silently replace and destroy the un-sealed over-cap history (EC-017).

**Backstop probe `stat()`-failure disposition — fail LOUD on any non-`NotFound` error, never
fail-open (NEW, BC-1.18.006 v1.5→v1.6, cluster-2 LOCAL adversary pass-2 finding F-C2-P2-003, MINOR,
edge case EC-019, invariant 8).** This AC's dedicated `Write`-arm backstop probe has exactly two
non-success outcomes: (1) `NotFound` — the canonical file does not yet exist (the artifact's
first-ever write, BC-1.18.005 EC-004's zero-byte-shard case); this is NOT a probe failure, and the
gate proceeds to apply the `Write` normally, exactly as if this backstop did not exist. (2) any OTHER
`stat()` error (`ELOOP`, `EACCES`, `EIO`, or any other failure) — the gate MUST fail LOUD, returning
`HookResult::Error` (NEW `E-SHD-008`, "backstop probe stat failure") WITHOUT applying the `Write`,
identically to how `Edit`/`MultiEdit`'s own pre-existing stat-failure disposition already behaves
(Invariant 8: no version of this backstop probe may fail OPEN on a `stat()` error other than
`NotFound`). **This WITHDRAWS a fail-open disposition** (log a warning, let the `Write` proceed) that
an earlier implementation adopted by analogy to cluster-1's already-adjudicated rule that "a `Write`
must never be blocked by a stat failure irrelevant to its own formula" — that rule correctly governs
BC-1.18.005's OWN stat-free `Write` trigger formula (left unchanged by this AC), but does NOT extend
to this AC's own dedicated backstop probe, whose entire purpose is to detect a crash-orphaned
over-cap canonical file before a `Write` can destroy it. Fail-open is UNSOUND here, not merely
under-specified: a canonical path whose FINAL path component is a symlink loop confined to itself
fails a dereferencing `stat()` (`ELOOP`) while `write_atomic`'s `rename(temp, canonical)` — which
does not need to dereference the destination's final symlink component — can still succeed, silently
replacing the symlink and applying the `Write`'s under-cap `content`, with the true, possibly-over-cap
content the symlink pointed at never examined, never sealed, and now unreferenced by the canonical
name. Fail-loud costs nothing in the common case and, in the rare failure case, produces an explicit,
actionable `HookResult::Error` rather than a silent, unverified pass-through of a `Write` whose safety
could not be confirmed (EC-019).

**Documentary note (non-AC, no code obligation — BC-1.18.006 v1.4 EC-016, mirrored on this story's
own EC-002 precedent, Edge Cases table below).** A `replace_all: true` call that triggers a
retroactive roll via AC-024's catch point (i) still returns `Continue` (not `Block`) to the agent —
no block/retry message is ever shown for the write that triggered the reconciliation, since the

new `HookResult` variant, and no code change beyond AC-024/AC-025's reconciliation logic itself
follows from EC-016 — this note exists purely to make the non-signal explicit and pre-empt a future
finding that would otherwise re-discover it.
