# VP-119: No Sealed Shard Ever Exceeds Its Recorded Cap, the Canonical Filename Is Never Renamed Away Across Any Roll Sequence, and Every Sealed Shard Is Write-Once/Immutable

## Property Statement

Over an arbitrary sequence of writes against a simulated sharded artifact, three safety invariants
hold at every step:

1. **No over-cap sealed shard.** For every `[[shard]]` entry the roll mechanism produces, its
   `bytes_at_seal` is `<= shard_cap_bytes` as recorded in the index at seal time (BC-1.18.006
   §Postcondition 3). Because the seal happens before the block and the blocked call is never
   applied, no downstream reader can ever observe a shard above its own recorded cap — this holds
   *relative to whatever cap is configured*, so it is independent of the F4-provisional numeric
   value.

2. **Stable current filename.** The canonical filename (e.g. `decision-log.md`) is never itself
   renamed to a sealed name across any roll sequence (BC-1.18.006 §Postcondition 6, §Invariant 3
   CORRECTED): `stat(canonical_path)` always succeeds and never resolves to a sealed inode from a
   prior roll — only the CONTENT behind the canonical name is replaced, via the
   copy-then-atomic-truncate-in-place seal (the pre-roll content is copied into a NEW
   `<stem>.<seq:04>.md` file, then the canonical is atomically truncated in place via `write_atomic`
   rename-ONTO-existing — never a rename-OUT of the canonical path, so the canonical path is never
   absent at any instant). Under this corrected mechanism the invariant is structurally, not merely
   conventionally, true.

3. **Sealed-shard write-once/immutability (NEW, v1.2 — BC-1.18.006 v1.8 §Postcondition 8, §EC-024,
   F-C2-P4-002).** No `[[shard]]`-eligible destination path is ever overwritten by a subsequent
   seal-publish attempt (`publish_sealed_shard`): before every `write_atomic` `rename(temp,
   <stem>.<seq:04>.md)` call — whether from a prospective roll (Postcondition 1 step (b)) or either
   of Postcondition 7's retroactive catch points — the gate first verifies the destination does not
   already exist. If it does, the gate returns `HookResult::Error` (`E-SHD-009`, "sealed-shard
   immutability violation") and applies NEITHER the seal nor any subsequent roll step (no truncate,
   no index publish); the pre-existing destination file is left byte-identical. This is DEFENSE-IN-
   DEPTH: it converts any residual `seq` collision — whatever its cause — into a loud, fail-safe
   error, never a silent overwrite of durably-sealed history. It is independent of, and layered on
   top of, the root-cause self-heal-first ordering fix for Postcondition 7 catch point (i)
   (BC-1.18.006 v1.8 corrected §Invariant 10, F-C2-P4-001; ADR-051 §Decision 16) — that root-cause
   fix is OUT OF SCOPE for this VP and is instead discharged by the pending, still-unallocated
   VP-NNN's EC-023 facet (F6-deferred, not self-allocated in this burst, per the EC-013..EC-022
   precedent).

## Proof Method

| Leg | Method | Tool | Coverage | Status |
|-----|--------|------|----------|--------|
| No-over-cap | proptest | Rust `proptest!` over arbitrary write sequences against a simulated artifact | property: every sealed shard's `bytes_at_seal <= shard_cap_bytes` | feasible-pending-harness (F4 code) |
| Stable-current-filename | proptest | Rust `proptest!` over arbitrary roll sequences | property: `stat(canonical)` always succeeds; canonical inode never equals any sealed inode | feasible-pending-harness (F4 code) |
| Write-once/immutability (NEW, v1.2, EC-024) | proptest | Rust `proptest!`/fixture: pre-create a file at a computed `next_seal_seq` destination before a roll attempts to publish there | property: `HookResult::Error`/`E-SHD-009` returned; pre-existing file byte-identical after the attempt; no truncate/index-publish side effect | feasible-pending-harness (F4 code) |

### Why proptest

Both are universally-quantified invariants over *arbitrary* write/roll sequences, not a fixed
fixture — proptest's generated sequences (variable payload sizes, interleavings) explore the state
space a hand-crafted table cannot. The property is stated relative to the recorded cap, so it is
value-agnostic and needs no F4 constant.

## Proof Harness Skeleton

```rust
// crates/factory-dispatcher/tests/proptest_shard_safety.rs
// VP-119: BC-1.18.006 PC3/PC6/INV3/PC8(NEW, write-once)/EC-024

proptest! {
    #[test]
    fn prop_no_sealed_shard_exceeds_recorded_cap(seq in arb_write_sequence()) {
        let mut art = SimArtifact::new(cap = arb_cap());
        for w in seq { art.apply_or_roll(w); }
        for shard in art.index().sealed() {
            prop_assert!(shard.bytes_at_seal <= art.index().shard_cap_bytes);
        }
    }

    #[test]
    fn prop_canonical_filename_never_sealed(seq in arb_write_sequence()) {
        let mut art = SimArtifact::new(cap = arb_cap());
        let canon = art.canonical_inode();
        for w in seq {
            art.apply_or_roll(w);
            prop_assert!(art.stat_canonical().is_ok());
            prop_assert_ne!(art.canonical_inode_now(), art.any_sealed_inode());
            let _ = canon;
        }
    }
}

// NEW (v1.2, EC-024): fixture-style test — no proptest generator needed, the collision is
// deliberately staged rather than arbitrary.
#[test]
fn sealed_shard_publish_refuses_to_overwrite_existing_destination() {
    let mut art = SimArtifact::new(cap = arb_cap());
    let next_seq = art.index().next_seal_seq();
    let dest_path = art.sealed_path_for_seq(next_seq);
    let pre_existing_content = b"unrelated pre-existing content";
    art.write_file_at(&dest_path, pre_existing_content); // simulates a residual collision

    let result = art.attempt_roll_publish_at(next_seq);

    assert!(matches!(result, Err(HookResult::Error { .. }))); // E-SHD-009
    assert_eq!(art.read_file_at(&dest_path), pre_existing_content); // byte-identical, untouched
    assert!(!art.index().has_entry_for_seq(next_seq)); // no index publish
    assert_eq!(art.canonical_size(), art.canonical_size_before_attempt()); // no truncate
}
```
