# VP-132: B2 BC-INDEX Body Split Content Preservation — SHA-256 of the Staged Per-BC-Row Content (BC-X.YY.NNN Rows Extracted From All Shards, Sorted by Canonical BC-ID) Equals `source_body_row_sha256` — Per-BC-Row Content Preserved Modulo the §Summary / §Subsystem Shard Manifest / Cross-Cutting-Invariant Sections

## Property Statement

The governed one-time B2 migration of `BC-INDEX.md`'s monolithic body into per-subsystem shard files
preserves content exactly. This is BC-1.18.008 §Postcondition 6a's exact analogue (VP-123), applied
to a CONTENT partition (by subsystem) instead of a time partition (by seal sequence). Because
`BC-INDEX.md`'s H1-per-BC-row is the POLICY-7 title source-of-truth, byte-level preservation here is
governance-integrity-critical, not cosmetic.

1. **Structured per-BC-row equivalence.** For any monolithic `BC-INDEX.md` body input, extract every
   `BC-X.YY.NNN` table row from ALL staged shard files — the union across the first-level per-subsystem
   shards (`shards/BC-INDEX-SS-NN.md`) and, where second-level sub-sharding applies (SS-05/SS-06, per
   VP-133), their ordered sub-shards — sort the extracted rows in canonical BC-ID order, concatenate
   the raw row bytes in that sorted order, and compute the SHA-256 → `staged_row_sha256`. The property
   asserts `staged_row_sha256 == source_body_row_sha256`, where `source_body_row_sha256` is the SHA-256
   of the SAME per-BC-row content extracted from the ORIGINAL (pre-split) `BC-INDEX.md` body in
   canonical BC-ID order, captured at quiescence (ADR-052 §Decision 5a drain step 5(c)). Excluded from
   BOTH the staged-row extraction and the source hash: `§Summary`, `§Subsystem Shard Manifest`,
   cross-cutting invariants, and non-row separator lines — only the `BC-X.YY.NNN` row entries are in
   scope, preserving the "modulo the newly-introduced §Subsystem Shard Manifest section" intent of the
   original content-preservation obligation (BC-1.18.011 §Postcondition 1). No BC-row content is lost,
   added, mutated, or reordered across the split. A whole-file concatenation SHA-256 against the
   original monolithic body (`source_sha256`, the whole-file fingerprint) is UNSATISFIABLE — the staged
   lean body ADDS the `§Subsystem Shard Manifest` section (extra bytes absent from the original) and
   reorders content, so a whole-concat round-trip is NOT the verified property (ADR-052 §Decision 7c
   step 3b F1); `source_sha256` is used ONLY by the step 5 fingerprint recheck (§Postcondition 3a),
   never here.

2. **Per-subsystem partition points are structural, never mid-row.** Partition boundaries fall only
   at `### SS-NN` section boundaries native to `BC-INDEX.md`'s structure (and, for SS-05/SS-06, at
   whole-`BC-X.YY.NNN`-row boundaries within the subsection) — never mid-row, so no BC's H1-per-row
   title text is ever split across two shard files.

The concrete `shard_cap_bytes` that determines WHETHER a subsystem requires second-level
sub-sharding is **PROVISIONAL-until-F4** (per BC-1.18.005 §Postcondition 6 / ADR-051 §Decision 2);
the content-preservation property itself holds for ANY cap and ANY per-subsystem partition, so it is
locked now. This is the identical provisional-scoping VP-123 carries (numeric cap only; preservation
structural).

## Proof Method

| Leg | Method | Tool | Coverage | Status |
|-----|--------|------|----------|--------|
| Structured per-BC-row equivalence | proptest / golden-file | Rust `proptest!` over synthetic monolithic `BC-INDEX`-shaped bodies (variable subsystem count, variable per-subsystem BC-row sets) + a golden round-trip against a committed snapshot of the real `BC-INDEX.md` body | property: `staged_row_sha256 == source_body_row_sha256` (SHA-256 of the canonical-BC-ID-sorted `BC-X.YY.NNN` rows extracted from ALL staged shards vs the same extraction over the original body; `§Summary` / `§Subsystem Shard Manifest` / cross-cutting-invariant / non-row lines excluded) | feasible-pending-harness (F4 code) |
| Structural partition boundaries | proptest | Rust `proptest!` asserting every partition point coincides with a `### SS-NN` (or, for sub-sharded subsystems, a whole-`BC-X.YY.NNN`-row) boundary | property: no BC row spans two shard files | feasible-pending-harness (F4 code) |

### Why proptest / golden-file

Content preservation is a universal round-trip property over arbitrary monolithic inputs (variable
subsystem sizes, variable BC-row boundaries) — proptest's generated fixtures plus a golden-file
round-trip against the real oversized `BC-INDEX.md` body give far stronger assurance than a single
hand-crafted example, exactly the assurance a governance-integrity-critical (POLICY-7 title-authority)
one-time migration demands. This mirrors VP-123's proptest+golden rationale for the mechanism-A
backfill-split. The independent census (every BC-ID in exactly one shard, cross-checked against
`total_bcs`) is a DISTINCT-method property proven separately by VP-133 (integration) per BC-1.18.011
§Invariant 2's "both checks independently mandatory, neither substitutes for the other."

## Proof Harness Skeleton

```rust
// crates/factory-dispatcher/tests/proptest_b2_bcindex_split_preservation.rs
// VP-132: BC-1.18.011 §Postcondition 1 — B2 body-split content preservation
// (structured per-BC-row equivalence, per ADR-052 §Decision 7c step 3b)

proptest! {
    #[test]
    fn prop_staged_rows_equal_source_body_rows(
        body in arb_monolithic_bcindex_body(),      // variable ### SS-NN sections, known BC rows
        cap in arb_cap(),                            // PROVISIONAL-until-F4; property holds for any cap
    ) {
        let out = shard_manager::b2_split_bcindex_body(&body, cap);
        // Extract every BC-X.YY.NNN row from ALL staged shards + sub-shards, sort by canonical BC-ID,
        // SHA-256 the sorted row bytes (§Summary / §Subsystem Shard Manifest / cross-cut / non-row lines excluded).
        let staged_row_sha256 = out.staged_bc_row_sha256();
        let source_body_row_sha256 = bc_row_sha256(&body);   // same extraction/sort over the original body
        prop_assert_eq!(staged_row_sha256, source_body_row_sha256);  // structured per-BC-row equivalence
    }

    #[test]
    fn prop_no_bc_row_spans_two_shards(body in arb_monolithic_bcindex_body(), cap in arb_cap()) {
        let out = shard_manager::b2_split_bcindex_body(&body, cap);
        prop_assert!(out.every_partition_at_structural_boundary());  // ### SS-NN or whole BC-row
    }
}
```
